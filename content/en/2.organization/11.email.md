# Email via Microsoft 365

The portal sends email to your users, for example invitations and password reset links. If you don't configure anything, the email is sent from the portal's default sender. With your own sender, the email instead comes from your domain and from a mailbox you own, for example `noreply@example.com`.

You set up the sender under **Settings → Email settings**. This requires the Organization administration permission.

This page describes how to send through Microsoft 365 with Microsoft Graph, which we recommend if you have Microsoft 365. If you use another email service, see [SMTP instead](#smtp-instead).

## What you need

- Microsoft 365 with Exchange Online.
- An account with the **Application Administrator** or **Cloud Application Administrator** role in Microsoft Entra, for the app registration.
- An account with the **Exchange Administrator** role, for the mailbox and the permission.
- The **ExchangeOnlineManagement** PowerShell module:

  ```powershell
  Install-Module ExchangeOnlineManagement -Scope CurrentUser
  Connect-ExchangeOnline -UserPrincipalName admin@example.com
  ```

- The ability to create DNS records for the sender domain (step 4).

## How it fits together

The portal signs in to Microsoft 365 as an app, with a client secret, and sends the email through Microsoft Graph from the sender mailbox. The app should be allowed to send as **that mailbox only** and no other.

::warning
Do **not** give the app the `Mail.Send` permission in Microsoft Entra. It applies to every mailbox in the organization. The restriction to one mailbox is made in Exchange Online (step 3), and it is **added to** what is granted in Entra; it does not subtract from it. If the app has `Mail.Send` in Entra, it can send as anyone, whatever the restriction in Exchange says.
::

The steps in brief:

1. Create a shared mailbox for the sender.
2. Register an app in Microsoft Entra and create a client secret.
3. Allow the app to send as the mailbox, and only that mailbox, in Exchange Online.
4. Make sure email from the domain passes DKIM and DMARC.
5. Enter the details in the portal.
6. Send a test email.

## Step 1: Create a shared mailbox

A shared mailbox needs no license as long as it is smaller than 50 GB, and nobody signs in to it. It works well as a sender.

```powershell
New-Mailbox -Shared -Name "Portal noreply" -DisplayName "Example Inc" -Alias portal-noreply -PrimarySmtpAddress noreply@example.com
Get-Mailbox noreply@example.com | Format-List PrimarySmtpAddress,UserPrincipalName,ExternalDirectoryObjectId
```

Keep the output. You need `UserPrincipalName` and `ExternalDirectoryObjectId` in step 5.

::note
Recipients see the mailbox's **display name** (`-DisplayName`) as the sender. The **Sender name** field in the portal does not change that when you send through Microsoft 365.
::

::tip
**Something went wrong?**

- *The domain is not accepted:* the address must be on a domain that is accepted in Exchange Online. Check with `Get-AcceptedDomain | Format-Table DomainName,DomainType`.
- *The address or alias is already in use:* choose another `-Alias`, or use the mailbox that already exists.
- *Wrong display name:* `Set-Mailbox noreply@example.com -DisplayName "Example Inc"`.
::

## Step 2: Register an app in Microsoft Entra

1. Open the [Microsoft Entra admin center](https://entra.microsoft.com) and go to **Entra ID → App registrations → New registration**.
2. **Name:** for example `Portal email`.
3. **Supported account types:** **Accounts in this organizational directory only (Single tenant)**.
4. **Redirect URI:** leave empty. Select **Register**.
5. Note the **Application (client) ID** and **Directory (tenant) ID** on the **Overview** page.
6. Under **API permissions**: remove `User.Read`, which is added automatically, so that the list is empty. Do **not** add `Mail.Send`.
7. Under **Certificates & secrets → Client secrets**: select **New client secret**. Choose a validity period and write down when the secret expires.
8. Copy the value in the **Value** column right away. It is shown only once. **Secret ID** is something else and does not work as the secret.

::tip
**Something went wrong?**

- *You copied the Secret ID, or didn't copy the Value in time:* create a new secret and delete the old one.
- *`Mail.Send` is listed under API permissions:* remove the row. If it has already been granted, that is not enough. Also go to **Entra ID → Enterprise apps → All applications →** the app **→ Permissions**, the **Admin consent** tab, select **…** next to `Mail.Send` and then **Revoke permission**.
::

## Step 3: Allow the app to send as the mailbox

The permission is granted in Exchange Online with *RBAC for Applications* and restricted to the mailbox with a *management scope*.

1. Open the app under **Entra ID → Enterprise apps → All applications** and note the **Application ID** and **Object ID**.

   ::warning
   Use the IDs from **Enterprise apps**. The Object ID under **App registrations** is a different ID and does not work here.
   ::

2. Run in PowerShell, replacing the values with yours:

   ```powershell
   # Connect the app to Exchange Online
   New-ServicePrincipal -AppId 11111111-2222-3333-4444-555555555555 -ObjectId 66666666-7777-8888-9999-000000000000 -DisplayName "Portal email"

   # A scope that covers only the sender mailbox
   New-ManagementScope -Name "Portal email - sender" -RecipientRestrictionFilter "PrimarySmtpAddress -eq 'noreply@example.com'"

   # Permission to send, restricted to the scope
   New-ManagementRoleAssignment -App 66666666-7777-8888-9999-000000000000 -Role "Application Mail.Send" -CustomResourceScope "Portal email - sender"
   ```

3. Check that the app reaches the sender mailbox and nothing else:

   ```powershell
   Test-ServicePrincipalAuthorization -Identity 66666666-7777-8888-9999-000000000000 -Resource noreply@example.com   # InScope: True
   Test-ServicePrincipalAuthorization -Identity 66666666-7777-8888-9999-000000000000 -Resource anna@example.com      # InScope: False
   ```

::note
The test command shows the change immediately, but sending through Microsoft Graph goes through a cache in Exchange Online. It takes **30 minutes to 2 hours** before a change applies. Every call from the app keeps the old cache alive for up to 2 hours, so don't test over and over. Wait about 30 minutes and test **once**.

`Test-ServicePrincipalAuthorization` only shows permissions in Exchange Online, not what is granted in Entra. So also check that the app does not have `Mail.Send` in Entra (step 2).
::

::tip
**Something went wrong?**

- *The scope points to the wrong mailbox:* change the filter. The change applies to every assignment that uses the scope.

  ```powershell
  Set-ManagementScope -Identity "Portal email - sender" -RecipientRestrictionFilter "PrimarySmtpAddress -eq 'noreply@example.com'"
  ```

- *Wrong ID in `New-ServicePrincipal`, for example the Object ID from App registrations:* remove the link and create it again with the IDs from Enterprise apps.

  ```powershell
  Remove-ServicePrincipal -Identity <wrong Object ID>
  ```

- *An assignment is wrong or exists twice:* list the assignments and remove the wrong one by its name.

  ```powershell
  Get-ManagementRoleAssignment -Role "Application Mail.Send" | Format-List Name,RoleAssigneeName,*Scope*
  Remove-ManagementRoleAssignment -Identity "<Name>"
  ```
::

## Step 4: DKIM and DMARC for the sender domain

The recipients' mail servers check that email from `example.com` really comes from you. If the domain has a DMARC policy with `p=reject` or `p=quarantine`, email sent through Exchange Online must pass **DKIM**, signed with your domain, or **SPF**. Otherwise it is rejected or ends up in the junk folder.

See the domain's policy:

```powershell
Resolve-DnsName _dmarc.example.com -Type TXT
```

Turn on DKIM for the domain in Exchange Online:

```powershell
Get-DkimSigningConfig -Identity example.com | Format-List Name,Enabled,Status,Selector1CNAME,Selector2CNAME

# If the domain is not listed, create the keys first
New-DkimSigningConfig -DomainName example.com -Enabled $false
Get-DkimSigningConfig -Identity example.com | Format-List Selector1CNAME,Selector2CNAME
```

Create two CNAME records in the domain's DNS:

| Name | Points to |
|---|---|
| `selector1._domainkey.example.com` | the value in `Selector1CNAME` |
| `selector2._domainkey.example.com` | the value in `Selector2CNAME` |

The values look roughly like `selector1-example-com._domainkey.example.n-v1.dkim.mail.microsoft`. Use exactly what `Get-DkimSigningConfig` shows.

When the records are visible in DNS, turn on signing:

```powershell
Set-DkimSigningConfig -Identity example.com -Enabled $true
Get-DkimSigningConfig -Identity example.com | Format-List Enabled,Status   # Enabled: True, Status: Valid
```

If you also want SPF to approve Exchange Online, add `include:spf.protection.outlook.com` to the domain's SPF record. It is not needed when DKIM works.

::tip
**Something went wrong?**

- *`Set-DkimSigningConfig` says the CNAME records are missing:* Microsoft cannot find the records yet. Check the spelling, especially hyphens and dots, and that the records are CNAME and not TXT. If your DNS service adds the domain name itself, enter only `selector1._domainkey` as the name. Wait a while and run the command again.
- *See what DNS answers:*

  ```powershell
  Resolve-DnsName selector1._domainkey.example.com -Type CNAME
  ```
::

## Step 5: Enter the details in the portal

1. Go to **Settings → Email settings**.
2. Select **Use organization-specific email provider**.
3. Choose **Microsoft Graph** under **Provider**.
4. Fill in the fields:

| Field | Value |
|---|---|
| **Sender address** | `noreply@example.com` |
| **Sender name** | For example `Example Inc`. With Microsoft 365, the mailbox's display name is what shows as the sender (step 1). |
| **Reply-to address** | An address where someone reads the replies, for example `support@example.com`. |
| **Tenant ID** | **Directory (tenant) ID** from step 2. |
| **Client ID** | **Application (client) ID** from step 2. |
| **Client Secret** | **Value** from step 2. |
| **Sender ID (optional)** | Leave empty if the mailbox's `UserPrincipalName` is the same as the sender address. Otherwise enter `ExternalDirectoryObjectId` from step 1. |
| **Endpoint (optional)** | Leave empty. |

5. Select **Save settings** and check that sending is enabled.

::note
The saved client secret is never shown again. If you leave the field empty while changing something else, it is kept. If you change **Tenant ID**, **Client ID** or **Endpoint**, you must enter the secret again.
::

## Step 6: Send a test email

1. Enter a **Test recipient** and select **Send test**. The test uses the values in the form, including the ones that are not saved.
2. If it succeeds, the portal shows that the test email was sent. If it fails, the portal shows what to do. Under **Technical detail** you find Microsoft's own answer, for example `ErrorAccessDenied` or `AADSTS7000215`.

If you just changed the permission in step 3, wait at least 30 minutes before you test.

::warning
A successful test means that Microsoft 365 has accepted the message for sending. If the recipient's server rejects it later, for example because DMARC failed, a bounce report goes to the sender mailbox instead. So check that the test email actually arrives, and look at the message headers. They should show `dkim=pass header.d=example.com` and `dmarc=pass`.
::

## Troubleshooting

| Message in the portal | What to do |
|---|---|
| "Microsoft 365 did not accept the client secret. Check that you copied the secret's value (Value), not its ID (Secret ID)." | Create a new secret (step 2) and paste its **Value** into **Client Secret**. |
| "The client secret has expired. Create a new one in the app registration and paste its value here." | See [Replacing the client secret](#replacing-the-client-secret). |
| "Microsoft 365 finds no app with that client ID in that tenant. Check Client ID and Tenant ID." | Compare with the app's **Overview** in Entra. Both IDs must come from the same app. |
| "Microsoft 365 finds no tenant with that ID. Check Tenant ID." | Use the **Directory (tenant) ID** from the app's **Overview**. |
| "Microsoft 365 refused to send: the app may not send as the sender. If the permission was just changed in Exchange Online, it can take up to two hours to apply – wait and test again. Otherwise the app lacks Mail.Send for this particular mailbox." | If you just did step 3: wait at least 30 minutes without testing, then try once. Otherwise run `Test-ServicePrincipalAuthorization` for the sender mailbox (step 3) and fix the scope with `Set-ManagementScope` if it does not return `InScope: True`. |
| "The sender does not exist in Microsoft 365. Check the sender address and Sender ID." | Check the address with `Get-Mailbox`. If `UserPrincipalName` differs from the sender address, enter `ExternalDirectoryObjectId` in **Sender ID**. |
| "The sender has no mailbox in Exchange Online. Use a shared mailbox or a user with an Exchange Online license." | Create a shared mailbox as in step 1 and use it as the sender. |
| "Microsoft 365 did not answer within 30 seconds. Try again in a moment." | Try again later. If it happens often, check the Microsoft 365 service status for your organization. |
| "Microsoft 365 refused the request …" | Open **Technical detail** and look up the code (`AADSTS…`) in Microsoft's documentation, or contact support and include the code. |

## Replacing the client secret

A client secret expires. Once it has expired, sending from your sender fails.

1. Create a new secret under **Certificates & secrets** in the app registration before the old one expires.
2. Paste its **Value** into **Client Secret** in the portal and select **Save settings**.
3. Send a test email.
4. Delete the old secret in Entra.

::tip
Put a reminder in your calendar a few weeks before the secret expires.
::

## SMTP instead

If you don't have Microsoft 365, or want to use another email service, choose **SMTP** under **Provider** and fill in **SMTP host**, **Port**, **Use encrypted connection (TLS)**, **Username** and **Password**. Common ports are 587 (STARTTLS) and 465 (implicit TLS).

For Microsoft 365 we recommend Microsoft Graph as described on this page. SMTP requires a user account whose password the portal stores, while Graph only lets the app send as a single mailbox.
