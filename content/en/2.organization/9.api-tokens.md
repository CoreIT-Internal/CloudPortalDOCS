# API keys

An API key lets a program or integration work against the modules' API on behalf of your organization — for example a DNS sync from a CI/CD pipeline. You find the page under **Settings** → **API keys**.

::note
To create or revoke API keys you need the **Organization administration** permission. If you lack it, an information box is shown and the buttons are disabled.
::

::warning
API keys created before this release have been revoked. They never worked against the API. Create new keys as described below.
::

## How an API key works

The top of the page summarizes the rules:

- "The key belongs to the organization and reaches only the modules' API – never sign-in, members or settings."
- "It only gets permissions you hold yourself and that can be lent. Sensitive permissions and administration of access are never included."
- "It is valid for at most 365 days and then ends by itself. A new key replaces an old one."
- "It goes dormant if the person who created it no longer administers the organization, and wakes up if that is restored."

## Overview of keys

The **API keys** list shows for each key:

- **Name** and **status**:
  - **Active** — the key works.
  - **Dormant** — the person who created the key no longer administers the organization, so the key does not work. Create a new key and revoke the dormant one.
  - **Expired** — the key's end date has passed.
  - **Revoked** — the key has been revoked.
- The beginning of the key, for example `msp_pat.abc123.••••`. The full key is never shown again after creation.
- The **permissions**, by name. Permissions the creator no longer holds are shown struck through — the key does not have them either.
- "Created by … · Last used … · Valid through …".

By default only active and dormant keys are shown. Tick **Show revoked and expired** to see all of them.

## Creating an API key

1. Click **Create API key**.
2. Enter a **Name**, for example "DNS sync from CI".
3. Choose **Permissions**. They are grouped as **The organization** plus one group per module, and you can use **Select all** per group. Only permissions you hold yourself and that can be lent are shown.
4. Choose **Valid through**: 30, 90, 180 or 365 days, or a date of your own. 90 days is preselected. The field is required and the key ends at the end of the day.
5. Click **Create key**.

### The key is shown once

Right after creation the key is shown: "Copy it now. It is never shown again and cannot be recovered – only replaced with a new one."

1. Click **Copy** and store the key in a safe place, for example a secrets manager.
2. Click **I have saved the key**.

::tip
Give each integration its own key with only the permissions it needs and a descriptive name. That makes it easy to see what a key is used for and to revoke the right key.
::

## Using the key

Send the key in the request's `Authorization` header:

```
Authorization: Bearer <your-key>
```

The key always starts with `msp_pat.`.

Try the key with the test call `GET /api/api-token`. The answer shows which key it is, which organization it belongs to and what it may do right now:

```bash
curl -H "Authorization: Bearer $CLOUDPORTAL_API_KEY" https://<your-portal>/api/api-token
```

::note
- The key reaches only the modules' API and the test call above — never sign-in, members or settings.
- Do not send the key from a browser where someone is signed in to the portal. A request that carries both a key and a signed-in session is rejected.
::

## Revoking an API key

1. Find the key in the list.
2. Click **Revoke**.
3. The button changes to **Click again to revoke**. Click once more to confirm.

The key stops working immediately.

::warning
Revocation cannot be undone. All integrations that use the key stop working — create and deploy a new key before you revoke the old one.
::

## Good practices

- Choose as short an end date as the integration can live with, and replace the key before it expires.
- **Revoke** keys that are no longer in use. The **Last used** information helps you find them.
- Keep an eye on **Dormant** keys when administrators leave or change role.
- Never share a key in email, chat or code that is checked into a repo.
