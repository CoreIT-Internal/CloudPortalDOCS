# Redirects

With redirects you send visitors from one address to another, for example from an old page to a new one, or from a whole domain to another website.

Redirects are published to **the edge**, the service that receives visitors' requests and answers with the redirect. For the edge to get the requests, the name has to point there in DNS. The portal takes care of that in the zone for you.

## Select a zone

1. Go to **Domains** → **DNS** → **Redirects**. You can also get there with **Manage Redirects** on the zone page.
2. The **Select Zone** list shows the organization's zones and how many redirects each zone has. The zones are shown as a grid. On a wide screen you can choose **Table** under **View as**.
3. Search with **Search zones** or sort the list, and click the zone.

Redirects belong to the zone's owner. Zones that another organization shares with yours are not shown here.

From here you can also import a file for several zones with **Import for several zones**. See [Import redirects](/en/domains-and-dns/import-redirects).

## The zone page

The zone header has the buttons:

- **Create Redirect** — see below.
- **Import** and **Export** — see [Import redirects](/en/domains-and-dns/import-redirects).
- **RewriteMaps** — groups of rules that are published together. See [RewriteMaps](/en/domains-and-dns/rewritemaps).
- **Test an address** — see [Test an address](#test-an-address).
- **Open DNS Manager** — the zone's DNS records.

On mobile, **Create Redirect** is shown as a button and the rest in the zone's menu (**…**).

### Status

The zone header shows how far the publication to the edge has come:

| Status | Means |
|---|---|
| **Active** | The edge serves the zone's redirects. If the edge has been probed it says, for example, "Active · behaviour verified (3 of 3)", or "Active · 2 of 3 probes correct" if an answer was wrong. |
| **Waiting to publish** | A change is on its way to the edge. |
| **Uploaded, activation unconfirmed** | The change has reached the edge, but it is not confirmed yet that it applies. |
| **Not published** | Nothing is published on the edge yet. |
| **Failing** | The publication gave up. Click **Publish again** under **Zone details**. |
| **Held** | The publication is stopped. Contact CoreIT if the status stays. |

### Zone details

Expand **Zone details** below the zone header to see:

- **Publication to the edge** with the **Hosts and DNS** list. A host is published on the edge only once all its name servers point here. Each host shows its state, for example "Active on the edge since …", "Points at the edge · goes out with the next publication" or "Does not point at the edge yet: …". The portal checks DNS by itself at regular intervals. If you changed DNS at another provider, you can click **Check DNS now**.
- **Observed requests at the edge** for 7, 30 or 90 days, and which rules got **Most requests, 30 days**. The figures are a lower bound: answers that browsers or a CDN take from their cache never reach the edge.

::note
The status and **Publication to the edge** are shown by default to the Owner, Admin and Operator roles.
::

## Create a redirect

Click **Create Redirect**. The panel has two kinds: **Forward a domain** and **Custom rule**.

### Forward a domain

Use **Forward a domain** when a whole domain should go to a new address.

1. Choose **Forward a domain**.
2. Under **Domain**: leave the field empty for the main domain, or type a prefix for a subdomain. The zone's name is already after the field.
3. Fill in **Destination URL**, for example `https://newsite.com`.
4. Under **Advanced** you can change:
   - **Include www.…** — also forwards `www`. Shown for the main domain and selected by default.
   - **Preserve paths** — selected by default. Then `/about` goes to `https://newsite.com/about`. If you turn it off, every visit lands on the destination's start page.
   - **Status code** — 301 and 308 are permanent, 302 and 307 temporary.
5. Click **Create forward**.

The forward shows in the list with the **Domain forward** badge. When you edit it, the domain and `www` cannot be changed, but you can change the destination, the paths, the status code and **Active**. With **Switch to custom** you edit the rule as a custom rule.

### Create a custom rule

Use **Custom rule** when you want to control single paths.

1. Choose **Custom rule**.
2. **Host** — leave empty for the zone itself, or type for example `www`. Below the field you see what the name becomes.
3. Choose the **Redirect Type**:
   - **Simple** — an exact path, for example `/old-page`.
   - **Wildcard** — `*` matches anything, for example `/products/*`.
   - **Regex** — a regular expression under the same rules as the edge (RE2), for example `^/blog/(.+)$`.
4. Fill in **Source Path**. It starts with `/`.
5. Fill in **Destination URL**, a whole address starting with `https://` or `http://`.
   - For **Wildcard**, what `*` matched goes in with `${1}`, for example `https://example.com/shop/${1}`. A `*` in the target is only a star.
   - For **Regex**, the groups go in with `${1}`, `${2}` and so on.
6. Choose the **Status Code**:
   - **Permanent** — "The edge answers 301 or 308 depending on the method. Browsers and search engines remember it."
   - **Temporary** — "The edge answers 302 or 307 depending on the method. Nobody remembers it."
7. Check the **Preview**, which shows what the edge will answer. For **Regex** you can type a path under **Try with path**.
8. Leave **Active** selected if the rule should apply right away.
9. Click **Create**, or **Save and create another** to continue with the next rule.

::note
Query parameters such as `?utm=…` are matched but not carried to the target. With **Regex** the query is carried if a group captures it. A path must not contain `//`, `/./` or `/../`.
::

::tip
Consider starting with **Temporary** while you try out a new destination. A permanent redirect is stored in visitors' browsers and is hard to take back.
::

## DNS for the redirect

For a redirect to work, the host's name has to point at the edge. The portal creates and maintains those DNS records in the zone. They are locked in the record table and badged **Redirect**, see [DNS records](/en/domains-and-dns/dns-records).

If a record that someone else created is in the way, you review the change before anything is saved:

- **Custom rule:** the panel shows "A DNS record for … is in the way" and which records are **Removed** and **Created**. Click **Change DNS and save**, or **Back**. If records are removed, the portal asks once more.
- **Forward a domain:** the **DNS records need to be updated** panel shows the same thing. Click **Update DNS and activate forwarding**.

This needs the **Edit DNS records** permission. If you lack it, the redirect is saved anyway: "Saved. The DNS change awaits approval by someone with DNS rights." The row is then badged **DNS awaits approval**, or **DNS needs DNS rights** for someone who lacks the permission themselves.

### Approve DNS

Someone with **Edit DNS records** approves the change:

1. Choose **Approve DNS** in the row's menu, or select several rows and click **Approve DNS (…)**.
2. The panel shows per host what is created, removed and kept. "The approval covers the plan exactly as shown."
3. Click **Approve**.

If the plan changes while the panel is open, nothing is approved and the new plan is shown.

::warning
When records that someone else created are removed, other traffic to the same name can be affected. Always review the plan before you approve.
::

## Manage the redirects

The list shows **Host**, **Path → target**, **Status** (permanent or temporary, and the type) and **Observed requests (30 d)** with when the rule was last seen. On mobile there is one card per rule.

- **Search** in the **Search redirects...** field.
- **Filter** by status and type, and **sort**, for example by **Most requests** or **Last seen**. On mobile the choices are under **Filters**.
- **Source**: **Standalone** shows rules that are not in a RewriteMap. **All effective** shows all the zone's rules, including those in RewriteMaps.

Badges on the rows:

- **Inactive** — the rule is switched off.
- **Domain forward** — the rule belongs to a forwarded domain.
- **RewriteMap: …** — the rule is in a RewriteMap.
- **Invalid rule** — "The edge would refuse this rule. It can be switched off, but not on until it is corrected."
- **DNS awaits approval**, **DNS changing**, **DNS held** or **DNS failed** — the state of the host's DNS.

### One rule at a time

Click **Edit** on the row, or **Copy target**. The row's menu has **View**, **Edit**, **Activate** or **Deactivate**, **Approve DNS** (when there is something to approve) and **Delete**. A greyed-out menu entry says why the action is not possible.

**View** shows every value with copy buttons. If the rule has changed, **Changed** says when, and that older hits are the rule's earlier behaviour.

### Several at once

Select the rows. On mobile, first click **Select**. Then choose **Activate Selected**, **Deactivate Selected**, **Approve DNS (…)** or **Delete Selected**.

**Delete Selected** shows the rules and the hosts they use before anything is deleted. A host's DNS records are removed only when no other redirect needs them. This cannot be undone.

## Test an address

With **Test an address** you see what happens to an address, step by step and rule by rule.

1. Click **Test an address** in the zone header.
2. Choose what to test:
   - **Draft** — what is saved now, as if DNS already pointed here. Nothing is sent to the edge.
   - **Published** — what is confirmed active on the edge. Changes that have not reached the edge are not included.
   - **Live** — what the edge answers right now, for a host the organization has published. "At most 10 live checks per minute."
3. Type an address, for example `customer.com/old-page`, and click **Test**.

The result shows each step, which rule took the address and where the visitor ends up. It also tells you if two rules take the same address, if there is a loop, or if there are more than five redirects in a row.

::note
**Live** makes a HEAD request. It is answered with 308 or 307 where an ordinary page view gets 301 or 302.
::

## Permissions

| Permission | Gives |
|---|---|
| **View redirects** | The zone list, the zone page, RewriteMaps and **Test an address** |
| **Create redirects** | Create redirects and add rules to a RewriteMap |
| **Edit redirects** | Edit, activate and deactivate. Also required to publish, unpublish, archive and verify RewriteMaps and change their matching options |
| **Delete redirects** | Delete redirects and RewriteMaps |
| **Import redirects** | Import a file. Creating, importing or re-importing a RewriteMap also requires **Create redirects** |
| **Export redirects** | Export |

Changing or approving DNS for a redirect also needs **Edit DNS records**.

By default the Owner, Admin and Operator roles have all the permissions. Member and Viewer can view and export, and Support can view. See [Roles and permissions](/en/organization/roles-and-permissions).
