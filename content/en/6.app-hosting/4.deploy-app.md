Open the app under **My apps** on the **Web apps** page, or search for it in the portal's global search. The app's page answers the most important questions first: is the app running, where is it, and do you need to do anything.

## Choose an environment

If the app has several environments, the **Environment** selector is shown at the top, for example with `production` and `staging`. Everything on the page applies to the environment you have chosen.

## Status and address

The status card at the top shows the app's state with a coloured dot and a short sentence:

| Status | What it means |
| --- | --- |
| **Running normally** | The app is in service and responding. |
| **We are working on your app** | Something is in progress right now. You do not need to do anything. |
| **We are preparing hosting** | The deployment plan is ready and CoreIT is preparing hosting. |
| **Not deployed yet** | The app has not been put into service. |
| **Something went wrong during deployment** | The latest deployment failed. |
| **The app is not responding** | The app did not respond at the latest check. |
| **We need to check something with you** | CoreIT needs to check something with you. |
| **Your app needs a few values from you** | The app is missing environment variables. |
| **Waiting for the domain to point here** | The domain's DNS does not point correctly yet. |
| **Waiting for you** | CoreIT is waiting for information from you. |
| **Status not verified** | The app is in service, but it has not been checked recently. |
| **We can't tell the status right now** | The portal cannot tell how the app is doing right now. |

Below the status is the app's address with **Open app ↗** and **Copy**, and the link **Use your own domain →**. A custom domain that is ready is shown instead of the platform's address. Read more in [Domains and publishing](/en/app-hosting/domains-and-publishing).

### On CoreIT Hosting

CoreIT Hosting builds the app from your repository, and you publish it yourself. The app gets an address on `coreitsite.app`, for example `myapp.coreitsite.app`.

Before the app has been published for the first time, the page says it gets the address when it is first published. Once the address is reserved, it says "It is the app's already, and starts answering when you publish for the first time." You can then already use it as the sign-in redirect address, for example in Entra ID or Google, and in the app's own settings.

Next to the status are three buttons:

- **Logs** — the app's own output. Under **Which lines**, choose between **All** and **stderr**, search the lines and select **Refresh** to read again. Known secrets are masked, but personal data may appear. CloudPortal keeps no copy of the log text.
- **Restart** — restarts the app.
- **Stop** — stops the app after you confirm with **Stop the app**. The status becomes "The app is stopped. Start it when you want it to answer again." and the **Start** button starts it again.

### In other hosting environments

Right below the status it says "The app is not running yet. This prepares the hosting environment and the deployment plan — CoreIT puts the app into service for you."

The **Deploy new version** button creates a new deployment plan, for example when you have changed the app. CoreIT does the actual deployment. The button requires the **Prepare deployments** permission.

Next to the button, another button may be shown when the status needs something from you: **Fill in values**, **Manage domain** or **Contact us**. If you need help, [contact support](/en/support/contact-support).

## Get started

An app on CoreIT Hosting that is not live yet shows **Get started**: "Three steps to a live app." Each step is ticked when it is done.

1. **Fill in environment variables** — with the **Fill in values** button. See [Secrets and environments](/en/app-hosting/secrets-and-environments).
2. **Build a version** — "Builds the app from your latest change in GitHub." with the **Build version** button.
3. **Publish** — once a version is built, with the **Go to publishing** button.

When the app is live, the list disappears.

## Facts about the app

The page shows four facts about the app:

- **Code** — the repository, as a link, and the branch in use. **Analyse again** reads in the latest code.
- **Hosting location** — where the app runs, for example **CoreIT Hosting**. "Managed by CoreIT."
- **Size** — for example **Micro** with "0.5 CPU · 1 GB RAM · 10 GB storage". "This is what the live version runs with." See [Change size](#change-size).
- **Environment variables** — for example "3 configured", and how many are missing if the app needs more values.

If values are missing, the box "Your app needs these values" is also shown, with one line per value, for example "Your app needs `DATABASE_URL` before it can be put into service."

If the code is on GitHub and the connection lacks permissions, a warning is shown with the **Manage GitHub connection** link. See [Connect GitHub](/en/app-hosting/connect-github).

When the repository has changed since the last analysis, "A new version is available in GitHub" is shown. The analysis requires the **Analyze repositories** permission.

## Versions

"A version is a change (commit) from GitHub that has been built. It goes live only when you publish it."

At the top of the section, the app's health is shown under **Operations**, and which version is live under **Publishing**. Below them is how the latest build went.

- **Build version** builds the latest change on the app's branch. The line below the button says which commit is built and when, and you can change that there.
- Each version has a row with commit, message, size, time and state, for example **Live**, **Ready**, **Standing by** or **Previously live**. Under **Details** and **Build log** you see more.
- **Publish** makes a built version live.
- **Roll back** makes an earlier version live again. The row says how long it takes.
- **Require approval before switching** means another person with the right to approve must approve each new version before it starts serving.

If a version has changed public values, its row says so, for example "Public values: ~ SITE_BOOKING_URL".

If a build fails, the reason is shown below the button. If it is something in the repository, for example a framework that is not built or a Node version that is not supported, see [Error codes and what to do](/en/app-hosting/for-ai-agents#error-codes-and-what-to-do).

## Environment variables

Under **Environment variables** you see and change the app's values, one per row. Each value is **Public** or **Secret**. Read more in [Secrets and environments](/en/app-hosting/secrets-and-environments).

## Change size

1. Select **Change size** under **Size**.
2. Under **Choose a size**, choose:
   - **Automatic size** — "We recommend and adjust the size to fit your app."
   - a named size. The size that fits the app is marked **Recommended**. If the size has a price, it is shown per month.
3. Select **Save size**. **Cancel** closes without changing anything.

CPU can be a fraction of a core, for example 0.5 CPU. If you choose **Automatic size** again, the platform takes over the choice. You need the **Change application settings** permission.

## Your app

Under the **Your app** heading you find:

- **Custom domains** — "Add your own name for the app, for example www.yourcompany.com. The app always answers on its platform address too." Select **Add domain**. Each domain shows the steps **Ownership**, **DNS**, **Connection**, **Certificate** and **Reachable**, and which DNS records to add. See [Domains and publishing](/en/app-hosting/domains-and-publishing).
- **Database** — "Connect an existing database or move it to CoreIT". The import does not move your database; it stays where it is.

## Advanced

The **Advanced** section stays closed until you open it. Changes here require the **Change application settings** permission.

- **App name** — "The name is shown in the portal. The address the app already has does not change." Save with **Save name**.
- **Deploy branch** — the branch that is built. For repositories on GitHub you pick the branch from a list; otherwise you type its name. Save with **Save branch**. When you change the branch, the analysis is re-run on the new branch.
- **Health path** — "The path the platform asks before a new version takes over traffic, and regularly afterwards." It should answer 200 when the app can serve, also to someone who is not signed in. Leave it empty for `/`, or choose one of the common ones, for example `/api/health`. Save with **Save health path**. The change applies from the next build.
- **Build configuration** — framework, runtime, package manager and build command. Save with **Save**, or select **Reset to detected** to go back to what the portal found.
- **Health checks** — monitor that an address responds. **Check now** checks right away. See [Domains and publishing](/en/app-hosting/domains-and-publishing#health-checks).

### In other hosting environments

There, **Advanced** also has:

- **CI/CD — delivery method** — choose how the app reaches the environment: **Manual deploy from the portal**, **GitHub Actions per release** (marked **Recommended**) or **GitHub Actions + manual deploy**.
- **Plan / preview** — "What will be created — before anything is applied." Shows, among other things, the delivery method, the environments and which secrets are used (names only, never values).

Under **CI/CD — delivery method** you see the workflow file that belongs to the delivery method.

1. Review the file.
2. Select **Download workflow.yml** if you want to add it yourself, or **Commit to repo** to add it directly.
3. Confirm "Commit the workflow to the repo?" with **Yes, commit**.

**Commit to repo** is only available for repositories on GitHub where the connection has write access. For other repositories, download the file and add it yourself.

::tip
To change the file, select **Customize workflow**, edit it and select **Save customization**. A customized file is marked **Custom**. With **Reset to generated** you go back to the portal's version.
::

## Close the app

**Close the app** is available for apps on CoreIT Hosting. The app stops answering, and the server it runs on is taken down.

- **What happens:** the address stops answering, also your own domains. The server the app runs on is taken down, and its capacity is freed.
- **What stays:** all versions, the app's data and your own domains.

Type the app identifier to confirm and select **Close the app**. The page shows the steps **Address**, **Server** and **Closed** while the app is closed. You start the app again by publishing a version. If you lack the permission to close the app, ask an administrator.

## Delete the app

At the bottom is the **Danger zone**. It is only shown if you have the **Delete applications** permission, which Owner and Admin have by default.

An app that runs on the platform cannot be deleted. Close it first under **Close the app**.

1. Open **Danger zone**.
2. Read the lists **This will be removed** and **This is NOT touched**. The app's environments, deployment plans, stored environment variables and domains are removed. Your Git repository and its code are not touched, and neither is your Supabase Cloud project.
3. Type the app identifier shown above the field.
4. Tick "I understand this permanently deletes the app and cannot be undone."
5. Select **Delete application**.

::warning
Deletion cannot be undone.
::
