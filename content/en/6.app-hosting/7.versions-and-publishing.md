# Versions and publishing

On CoreIT Hosting, every build of the app becomes a **version**. You decide when a version goes live. If something goes wrong, you go back to an earlier version.

::note
Versions are only available for apps that run on CoreIT Hosting. In other hosting environments, CoreIT puts the app into service for you. See [Your app](/en/app-hosting/deploy-app).
::

## How it works

- CoreIT builds the app from your repository. Every build becomes a new version in the list. You do not order the build yourself.
- When you publish a version, it starts beside the version that is live. Traffic switches only once the new version answers.
- If the new version never becomes ready, no traffic is switched. The version that was live keeps serving the app.
- After a switch, the previous version keeps running for a while. You can then go back to it in a few seconds.

## The Versions panel

The **Versions** panel is on the app's page, right below the status card. If the app has several environments, the panel applies to the environment you have chosen under **Environment**.

While a publication is in progress, the panel updates by itself.

### Operation and Publishing

At the top of the panel are two lines. They show different things.

**Operation** shows whether the app answers: **Available**, **Unavailable** or **Not verified**. Next to it is when the app was checked, for example "checked 14:05". If the app has not been checked recently, it shows when the last check was made instead, "last check …".

**Publishing** shows what is happening with the versions:

| The line says | What it means |
| --- | --- |
| "Version a1b2c3d is live" | The version is serving the app. |
| "Version a1b2c3d is being published" | A publication is in progress. |
| "Version a1b2c3d is waiting for approval (requested by …)" | The version is ready and waiting for another person to approve it. |
| "The latest update failed. The previous version is still serving." | The new version did not go live. The app runs as before. |
| "We don't know yet whether the switch went through. Nothing can be changed until that is settled." | The portal is waiting to hear how the switch went. Meanwhile, nobody can publish, approve or roll back. |
| "No version is published yet" | No version has been live in the environment. |

::note
A failed publication does not mean the app is down. Look at the **Operation** line to see whether the app answers.
::

While a publication is in progress, the **Publishing** line shows which step it is on and since when:

1. **Waiting for its turn**
2. **Preparing**
3. **Starting the new version**
4. **Checking that the new version answers**
5. **Switching traffic**

If approval is required, it also says "Once it is ready, another person has to approve before traffic switches."

### The list of versions

The versions are listed newest first, in the columns **Version**, **Built**, **State** and **Actions**. On a narrow screen each version is shown as its own card.

A version is named after its commit, for example `a1b2c3d`. The commit message is shown below the name. If two versions were built from the same commit, when they were built is shown as well. Select **Show more** to see older versions.

| State | What it means |
| --- | --- |
| **Ready** | The version is built but has not been live in the environment. |
| **Publishing** | A publication of the version is in progress. |
| **Waiting for approval** | The version is ready and waiting for approval before traffic switches. |
| **Live** | The version is serving the app now. |
| **Standing by** | The version is not live, but it is still running. |
| **Failed** | The latest publication of the version failed. |
| **Declined** | The switch to the version was declined or withdrawn. |
| **Expired** | The version waited for approval for more than 7 days. |
| **Previously live** | The version has been live, but it no longer runs. |
| **Unknown** | The portal does not know yet whether the switch to the version went through. |

If CoreIT has not built any version yet, it says "No version has been built yet" and "Waiting for the first build".

If it says "The versions could not be loaded", select **Try again**.

## Publish the latest version

If the latest version is not live, the panel shows the **Publish latest** button, followed by the version's name.

1. Select **Publish latest**.
2. The portal asks "Publish version …?". Read the confirmation.
3. Select **Publish**, or **Cancel**.

The new version starts. Once it answers, traffic switches to it.

If the latest version is already live, it says "The latest version is live".

If the button cannot be used right now, it is greyed out and the reason is shown next to it. For example "An update is already in progress".

## Actions on a version

Each row in the list shows the actions you can use:

- **Publish** — publish a version that has not been live in the environment. You can publish a version that is **Failed**, **Declined** or **Expired** again.
- **Roll back** — go back to a version that has been live. See [Roll back](#roll-back).
- **Approve and switch** — approve a version that is waiting for approval.
- **Decline** — say no to a version that is waiting for approval.
- **Withdraw** — take back your own request while it is waiting for approval.
- **Details** — see how the publication of the version went. See [Details of a publication](#details-of-a-publication).

Only one publication at a time can be in progress in an environment. An action that cannot run right now is greyed out, with the reason next to it. For example "An update is already in progress" or "Waiting for approval of version a1b2c3d". An action you do not have permission for is not shown at all.

## Roll back

Select **Roll back** on the row of the version you want to go back to. How long it takes depends on the version:

- **The version that was live just before** — if it is still running, it says "The previous version is still running, so the switch takes a few seconds." You need the **Publish and switch versions** permission.
- **An older version** — "This version no longer runs, so it is started again. That takes a few minutes." You need the **Manage deployments** permission.

The same applies to the version just before if it no longer runs, or if the secrets have changed since it started. In the latter case it says that the version is started again with the current secrets, so no value that was removed comes back.

A version that is started again is called a cold rollback. It is only possible while the version's image (the built package) is still available. Otherwise **Roll back** is greyed out, with "Cannot be started again: the version’s image is no longer available".

The portal asks "Roll back to version …?". Select **Roll back**, or **Cancel**.

::warning
A rollback restores the code, not the data. The version you go back to meets the data as it is now, including what the newer version changed. The secrets do not come back either, see [Secrets and rollback](#secrets-and-rollback).
::

## Require approval

With the **Require approval before switching** checkbox you decide that a second person must approve before a new version starts serving. The checkbox is only shown to people with the **Approve switches** permission. It applies to the environment you have chosen.

Below the checkbox it says: "Another person who may approve must approve every new version and every cold rollback before it starts serving. Going back to the version that was live just before needs no approval, so a fault can be undone in seconds."

A change applies to publications that start after the change. A publication already in progress keeps the requirement it started with.

### How an approval works

1. Someone publishes a version. The confirmation says "Another person who may approve has to approve before traffic switches."
2. The new version starts and is checked. Once it is ready, the publication stops. The **Publishing** line shows "Version … is waiting for approval (requested by …)". Traffic still goes to the version that is live.
3. Another person with the **Approve switches** permission selects **Approve and switch** on the version's row.
4. The confirmation "Approve and switch to version …?" shows the commit message and who requested the switch. Select **Approve and switch**.

Traffic switches to the new version.

If you do not want the version, select **Decline**. The person who requested the switch can select **Withdraw** themselves. Neither asks for confirmation. The version is marked **Declined** and has never served any traffic. It can be published again later.

### Approval rules

When the requirement is on:

- You can never approve your own request. On your own request, **Approve and switch** is greyed out, with "Another person who may approve has to approve".
- A request that is not approved within 7 days expires. The version is then marked **Expired**.
- Going back to the version that was live just before needs no approval, as long as it is still running. The confirmation then says "No approval is needed: this is the version that was live just before, and it is still running."
- A cold rollback needs approval, just like a new version.
- While a version is waiting for approval, no other version can be published in the environment.

## Confirmations

Every publication, rollback and approval asks for a confirmation. The question names the version with its commit and build time. The confirmation also shows the commit message and, where it applies, whether an approval is required.

| Action | The portal asks | Confirm with |
| --- | --- | --- |
| Publish | "Publish version …?" | **Publish** |
| Roll back | "Roll back to version …?" | **Roll back** |
| Approve | "Approve and switch to version …?" | **Approve and switch** |

All three remind you that both versions run against the same data during the switch:

- When you publish or approve: "During the switch both versions run against the same data. The new version has to work with the data that exists."
- When you roll back: "During the switch both versions run against the same data. The version you go back to has to work with the data as it is now, including what the newer version changed."

**Decline** and **Withdraw** ask nothing.

## Details of a publication

Select **Details** on a version's row. **Details** is available for versions that have been published at least once. The "Publishing version …" panel shows:

- **The version** — the commit message, who wrote it and when. If the code is on GitHub, there is a **View the commit** link. If another version is live, there is also **Compare with live (…)**, which shows what has changed since that version.
- **State**, **Started** and **Finished** for the publication.
- **Reason** — why the publication failed, for example "The version started but never became ready for visitors, so no traffic was switched to it." Under **Technical details** there is an error code. Give it if you [contact support](/en/support/contact-support).
- **The log** — the end of the version's log, when the version never became ready. The log is cleaned of the environment's secrets before it is stored. If it cannot be checked, it is not shown: "The log can't be shown because it could not be checked against the environment's secrets."
- **Approval** — who requested the switch, when the request expires, and who approved or declined it.

## Secrets and rollback

A version runs with the secrets that existed when it started. If the secrets change after that, the live version shows: "The secrets have changed since this version started. It runs with the previous values until a version is published."

A rollback never brings back old values. The version you go back to starts with the current values. Read more in [Secrets and environments](/en/app-hosting/secrets-and-environments#secrets-and-versions).

## Permissions

| What you want to do | Permission | Included by default for |
| --- | --- | --- |
| See the versions and their details | **View deployments and logs** | Owner, Admin, Operator, Member, Viewer, Support |
| Publish a version, go back to the version that was live just before, and withdraw your own request | **Publish and switch versions** | Owner, Admin, Operator, Member |
| Approve or decline a switch, and change **Require approval before switching** | **Approve switches** | Owner, Admin, Operator |
| Roll back to an older version (cold rollback) | **Manage deployments** | Owner, Admin, Operator |

::tip
By default, Member can publish but not approve. If you want another person to always review a new version, turn on **Require approval before switching** and give **Approve switches** to the people who review.
::

Read more under [Roles and permissions](/en/organization/roles-and-permissions).
